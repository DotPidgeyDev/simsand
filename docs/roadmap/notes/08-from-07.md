# Milestone 08 notes, from closing Milestone 07

**Written:** 2026-11-25, closing Milestone 07  
**Use when:** starting world director and storytelling

## What the world already does

A living character picks one action from the scored definitions in
`packages/simulation/src/systems/actions.ts`. The catalog runs through
`buy`. Commitment is five seconds. An urgent need at 0.8 interrupts and
cools the cut-off action for 20 seconds.

The log, memories, and relationships are one record per fact, indexed
by participant and pair. The live log keeps the newest 10,000 events.
SQLite keeps the newest 100,000 (`SIMSAND_LOG_RETENTION`). Inspection
history merges stored rows with the live window. Schema version is 6.
Saves are format version 24. Restart resumes at the saved tick.
Downtime is not simulated.

Viewers are server-issued rows. Twitch accounts map through
`platform_identities`. One viewer owns at most one character. Death
does not free that slot; removing the character does. Viewer create
goes through `CommandGateway`. The request cannot name its issuer.
`character.created` stays on the command result. It is not a
simulation-log event and is not in `simulation_events`.

Chat `!join` and local `POST /platform/chat` create characters. Short
viewer feedback is a presentation string over the command outcome.
Bans refuse commands without deleting the character or its history.

The browser snapshot still carries position, terrain, and the resting,
eating, drinking, working, and lifecycle flags. Inventories and piles
are on the saved world and on inspection, not on the map snapshot.

Regression for Milestones 03–07 is in
`packages/simulation/src/regression.test.ts`. Viewer command routes,
receipts, bans, Twitch parse, and feedback are covered under
`apps/server/src/`.

## What Milestone 08 will find in the way

1. **The chronicle must read the existing log.** Do not invent a second
   event model for stream stories. Score and filter
   `simulation_events` / the live log. A viewer's public history is a
   window over participants, not a copy stored on the character.

2. **Command receipts are not chronicle material.** `character.created`
   and gateway results stay outside `simulation_events` unless a later
   rule deliberately writes a world fact. Greetings, gifts, and trades
   already are world facts.

3. **Viewer feedback is not the director.** Chat replies are
   command-outcome presentation. The world director reacts to recorded
   simulation events for camera focus and stream priority. Do not drive
   ordinary AI from Twitch chat text.

4. **Streamer interventions use the existing command boundary.** The
   gateway already allows `streamer` to create and remove. New
   intervention commands should become `SimulationCommand` values the
   server issued. Do not let the presentation layer mutate ECS state.

5. **Inventories and piles are on the render snapshot.** They remain
   saved and inspected. Putting them on the wire did not bump the save
   format. That was presentation, not a new economy.

6. **Catalogs are append-only, and component arrays are process-global.**
   Save format 24 has `viewerId`. Adding snapshot fields for stacks
   does not require a new save version unless the persisted world
   changes. A second `createSimulationWorld` in the same test still
   overwrites the first world's slots.

7. **Tick performance is a Milestone 10 concern.** At 1,000 entities the
   pure tick is about 4–5 ms (under the 10 ms guardrail).
   `updateActions` is most of that. Do not divert this milestone into
   action-loop optimisations unless a new director feature blows the
   budget. Goals and the deferred wins are in
   `docs/architecture/simulation.md` §14 and Milestone 10.

## Suggested first increment

Detect one consequential log event type that already exists (for
example a completed greet or trade), emit a scored chronicle entry
from that record, and expose it for inspection without changing how
characters choose actions.

## What the first increment decided

A completed `character.greeted` is the first chronicle type. Scoring is
a presentation pass over the existing participant log, not a second
store and not a simulation write.

- `chronicleFromEvents` / `chronicleEntryFromEvent` live under
  `packages/simulation/src/storytelling/`.
- `inspectCharacterChronicle` returns the scored window for one
  character. `GET /entities/:id/chronicle` scores the same merged
  retained+live history the history route already builds.
- Tier for a greeting is `notable` (score 0.35). Ordinary
  `action.ended` rows are skipped.
- Character action selection is unchanged.

## What the second increment decided

Every consequential social and economy log type now scores into the
chronicle. Ordinary `action.ended` rows still stay out.

- Comfort, keep, and bluff are `notable`. Confide and trade are
  `significant`.
- Summaries name the initiator, the other participant, and for gifts
  or trades the item quantities already on the log payload.
- Still no second event store and no change to action selection.

## What the third increment decided

Inventories and resource piles ride on the render snapshot. That is
presentation over state that was already saved and inspected. The
persisted world version stays at 24.

- `EntitySnapshot.inventory` is the character's sparse stacks.
- `WorldSnapshot.nodes` is the live pile list, sorted by tile.
- A delta carries changed entities (including inventory) and replaces
  `nodes` only when a pile appears, changes, or disappears.
- The browser redraws piles from that list. Character action selection
  is unchanged.

## What the fourth increment decided

Presentation tiers from `docs/design/storytelling.md` §5 are now a rule
in `@simsand/shared` (`CHRONICLE_PRESENTATION`): notable and above go to
the feed, significant and above notify, dramatic and above take camera
focus.

- `chronicleSince(world, cursor)` scores only events written since the
  previous `nextLogId`. It reads the log tail, not the whole log.
- The worker starts its cursor at the restored `nextLogId`, so a
  restart does not replay old history into the feed.
- The server's feed is in memory and lost on restart. The log in SQLite
  stays the durable record.
- A notification pulses a ring around the participants. Nothing is
  dramatic yet, so camera focus has no trigger. Death and director
  interventions are the likely first dramatic events.
- A delta whose only change is the pile list is now sent. Before this,
  the worker dropped it.
