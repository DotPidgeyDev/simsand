# Milestone 04 notes, from closing Milestone 03

**Written:** 2026-11-16, closing Milestone 03  
**Use when:** starting interaction and social behaviour

## What the world already does

A living character picks one of `idle`, `move`, `eat`, `rest`, `drink`,
`work` from scored definitions in
`packages/simulation/src/systems/actions.ts`. The same lifecycle
records `completed`, `interrupted`, and `failed`. Commitment is five
seconds. An urgent need at 0.8 interrupts and cools the cut-off action
for 20 seconds. Inspection already shows the action, biased scores,
availability, cooldowns, and the last ending.

Characters do not see each other. Movement does not step around a
neighbour. A camp is a workplace for a solo visit that produces
nothing. Several people can occupy the same tile.

Personality is stored as ten traits, 0 to 1. Only **curiosity** (idle
versus move) and **industriousness** (work, and whether they walk to a
camp) are read. The other eight remain stubs.

Needs are still only hunger, thirst, and fatigue. Adding a fourth need
is a save-format change.

Relationships and memories do not exist. Sparse records keyed by
stable ID are the planned home, not an ECS all-pairs matrix (ADR 003).

## What the original Milestone 04 scope assumed

The original list is still the right shape: interactions, sparse
relationships, social actions, memories, outcomes, social motivation,
and events from real simulation results.

Lessons from the action cycle that change how to start:

1. **Social actions are more action definitions**, not a second
   decision loop. They need `score`, `ready`, `holds`, `sustain`,
   `urgent`, and the same three endings. Greet is like work, not drink:
   with nobody adjacent they idle or move, and do not log a failed greet.
   Failure is for a greeting that started and then lost its target.
   A later seek-a-person action can fail like a drink with no water.

2. **Do not add a social need on day one.** `BASIC_NEEDS` is hunger,
   thirst, and fatigue. Sociability can first work like industriousness:
   a preference among existing idle, move, and a new social action
   while those three needs are quiet. A belonging need waits until that
   preference is not enough, and it bumps the save version.

3. **One interaction, one relationship record, one memory kind, one log
   event.** A completed social action creates or updates a sparse record
   and, when the event is consequential, one memory. Ordinary proximity
   is not a memory. Do not log every tick two people share a tile.

   The same rule applies to the debug log. Write one event with both
   participant IDs; character history is an index, not "A interacted
   with B" plus "B interacted with A". Memories and later viewer
   chronicle entries should point at that event rather than restating
   it.

4. **Wire traits only when the action reads them.** Milestone 04 is
   the first reader for sociability, empathy, loyalty, and honesty.
   Leave aggression and courage for conflict, greed for economy,
   ambition for goals.

5. **Camp is already work.** Do not silently turn it into a meeting
   hall. If people gather, that is a new target or a new action, not a
   reuse of `work`.

6. **They currently share tiles.** Tests that need two bodies should
   use one world and two entities. Component arrays are process-global;
   a second `createSimulationWorld` in the same test reuses bitECS
   handles and overwrites the first world's slots.

7. **Events stay outcomes.** ADR 004: nothing in presentation invents
   a meeting. Inspection can show a relationship the way it shows an
   action score. Domain events wait until the simulation has recorded
   the interaction.

   Milestone 04 is the log/monitor pass: extend inspection so a
   character's history can be listed from those events. Do not wait for
   Milestone 08's chronicle or Milestone 10's admin UI. Durable storage
   of the same log is Milestone 06; a filtered viewer window is
   Milestone 08.

8. **Knowledge is still missing.** A character should not target a
   person they have no way to know about. Until discovery exists, the
   first social action should use presence: someone on a neighbouring
   or same tile, not a global search of the population.

9. **LLM stays out of the tick.** Dialogue from recorded state can
   wait. Summaries of memories are a later consumer, not a producer of
   facts.

## Suggested first increment

Add one social action that can only start when another living
character is adjacent, keep it on the existing action list (append-only
`ACTION_IDS`), score it with sociability while needs are quiet, and on
`completed` write a sparse relationship keyed by the two stable IDs.
Inspect it. Leave inventory, combat, and camp-as-gathering for later
milestones.

**Done (2026-11-18).** `greet` is in the action list. Completing it
writes one relationship and one log event with both participants.
Inspection shows relationships; `GET /entities/:id/history` lists that
character's events. The first meeting also writes one `greeting` memory
that points at the event. Saves are version 14. Memory and log lookup
is still a linear scan of a world list; Milestone 06 indexes that store
by participant and pair. If a social action here starts reading memories
in the tick, add that index first rather than filtering the array every
entity every tick.

**Comfort (2026-11-18).** `comfort` reads empathy. It can start only
beside a living neighbour whose hunger, thirst or fatigue is above 0.3,
and only while the actor's own needs are quiet. It aims at the
neighbour with the highest of those needs. Completing it updates the
same relationship greet uses and writes one `character.comforted`
event. The first comfort between a pair is one `comforting` memory.
Saves are version 15. Loyalty and honesty are still unread. Do not add
a belonging need until idle, move, greet and comfort are not enough.

Regression for Milestone 03 is in
`packages/simulation/src/regression.test.ts`. Do not change those
expectations to make a social action fit; extend the list.
